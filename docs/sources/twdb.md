# TWDB Water Data for Texas

Verified 2026-11-23 from the build machine: all calls HTTP 200, 1–15 s.

## Endpoints
- All lakes: `https://www.waterdatafortexas.org/reservoirs/recent-conditions.json` (74 KB, 123 keys).
- Lake list with CSV slugs: `https://www.waterdatafortexas.org/reservoirs/statewide` (links `reservoirs/individual/<slug>`).
- Last 30 days: `https://www.waterdatafortexas.org/reservoirs/individual/<slug>-30day.csv` (~4 KB, with a `#` header).
- Full history: `https://www.waterdatafortexas.org/reservoirs/individual/<slug>.csv` (0.2–1.9 MB). **Some full-history files have no `#` header at all** (tawakoni, texoma, toledo-bend, travis, tyler, whitney on 2026-11-23): read the datum from the 30-day file.
- `statewide.json` is a 404.

## Key to slug
JSON key → CSV slug: split CamelCase into words, split runs of capitals into initials, lower-case, hyphens (`ChokeCanyon` → `choke-canyon`, `BASteinhagen` → `b-a-steinhagen`, `OHIvie` → `o-h-ivie`, `Lake O' the Pines` → `lake-o-the-pines`). Exception: `BoisDArc` → `bois-darc`. Stored per lake as `primary.twdb_slug` (and `csv_slug`). All 123 keys map to a slug on the statewide page.

## Fields (JSON, per key)
`full_name`, `short_name`, `condensed_name`, `timestamp` (date the daily average covers), `elevation` (ft), `percent_full`, `conservation_pool_elevation`, `dead_pool_elevation`, `conservation_storage`, `conservation_capacity`, `volume`, `volume_under_conservation_pool_elevation`, `area`, `flood_control_lake` (null or "Y"), `gauge_location` {coordinates [lon, lat]}, `tags`.

CSV columns: `date, water_level, surface_area, reservoir_storage, conservation_storage, percent_full, conservation_capacity, dead_pool_capacity`.

## Quirks
- `timestamp` for some lakes is today's date (a partial-day average); others are yesterday.
- `percent_full` is capped at 100 (conservation storage is capped at capacity): use elevation − conservation pool for "above full pool".
- `Addicks` and `Barker` (flood-detention reservoirs): `percent_full` and capacity are null and the conservation pool equals the dead pool (67.5 ft / 70.0 ft). Mapped with `full_pool_ft: null` (level only).
- The 30-day header states the vertical datum (`Vertical datum(s) used`), e.g. `NGVD29` (92 lakes), `NAVD88` (10), offsets such as `NAVD88 +0.26` (Buchanan), `NGVD29 -43.3` (Elephant Butte), and dated changes (Bridgeport, Brownwood, Eagle Mountain, Nasworthy, Red Bluff switched to NAVD88).
- Seasonal conservation pools appear in the header (Elephant Butte, Lake O' the Pines, Wright Patman; Buchanan until 2024). The JSON's `conservation_pool_elevation` is the value TWDB applies now, so the pipeline should read it on every run.
- TWDB values are built from USGS/USACE/IBWC/LCRA gauges; for ~105 lakes a USGS gauge at the same point matches TWDB to ±0.10 ft (see `docs/mapping/usgs.md`).
- Gaps: the plan's earlier helper saw a gap in one 30-day download. Check dates for gaps.

## Bad values in the history files
The full-history CSVs contain isolated spikes and short runs of impossible values, e.g. Elephant Butte 3147.97 ft on 2026-09-09 (recent), Oak Creek and Proctor 246200.00 (a storage figure in the level column) in January 2003, B. A. Steinhagen 0.00 / 9.6 / 986 ft in 1987–1990, Pat Mayse 50–55 ft in 1987–1996, Lake Marble Falls 820.98 ft in 1995. `tools/map_lakes.py` drops values more than 15 ft from the median of their neighbours before computing the validation range (list per lake in `docs/mapping/evidence.json`, `history_spikes_dropped`). Backfill and the jump hold must expect the same.
